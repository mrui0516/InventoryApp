# 货架状态图（Shelf map）

## 为什么不是「库存数量」

手机壳不数个数。店员站在货架前要在一秒内回答两件事：

1. **有没有货？**
2. **货架上方的盒子里还有没有？**

不是「还剩几个」。数个数是没人会长期维护的工作，而**没人维护的数字比没有数字更糟**——
它会让人相信一个错的数。

所以每个 **款式 × 型号 × 颜色** 只有一个状态：

| 状态 | 含义 | 图标 |
|---|---|---|
| `OUT` | 没货了 | `–`（虚线框） |
| `DISPLAY` | 货架上有，且**就这些** | `●`（绿） |
| `EXTRA` | 货架上有，**上方盒子里还有** | `▲`（蓝） |

卖完了点成 OUT；上方的货全部补到货架后，把 EXTRA 点成 DISPLAY。都不需要填数字。
点一下格子按 `OUT → DISPLAY → EXTRA → OUT` 循环——这正是现实中发生的顺序。

## 数据结构

**不存** `"IP15 Pro: B(up), T"` 这种文字。四件事各自独立：

| 表 | 作用 |
|---|---|
| `CaseStyle` | 款式：Normal silicone / MagSafe / … |
| `DeviceModel` | 手机型号（复用已有的机型表，带品牌和别名） |
| `ShelfColour` | 颜色，店里自己加 |
| `CaseStock` | 上面三者的组合 + 一个 `state`（唯一约束） |

**行是懒创建的**：从没上过货的格子根本没有行，读起来和 OUT 一样。

**扩展性**：`state` 故意不是两个 boolean。以后加 `quantity`、进货、出货、采购、
销售时，现有每一行**仍然有意义**，不需要推翻重来。真正的通用型号关系
（`CompatibilityGroup`）已经存在，随时可以接上。

## 排序

`DeviceModel.sort_key` 把数字**补零**后存下来，所以 `iPhone 9` 排在 `iPhone 11` 前面
（纯字母序会反过来）。排序键是存下来的，**新加的型号自动落到正确位置**，
不需要重排。品牌用 `regroup` 分组显示。

## 通用型号

现阶段**只写备注、不同步状态**（店里的决定）。备注是给货架前的人看的提醒
（"和 14 Pro 通用"），两个型号的状态各自独立标记。备注**可被搜索**。

## 权限

- **改状态**：任何登录用户。标记缺货是站在货架前的人的工作，不该等经理。
- **加型号 / 加颜色 / 加款式**：经理。

## 页面

`/shelf/`（侧栏 Shelf）。搜索框**边打边筛**，没有 Apply 按钮；
筛空的品牌标题会自动隐藏。型号列**横向滚动时固定**在左边。
**没有照片**——一个黑色壳的照片和另一个黑色壳的照片没有区别。

初始化：`python manage.py seed_shelf --apply`（默认 dry-run），
建 Normal silicone 款式和 10 个常用颜色，之后全部在页面上增改。
