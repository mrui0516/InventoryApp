# 客户端批发目录：账号与登录（第一期）

> 日期：2026-11-07。状态：店主已确认（72 小时、14 天、页头用店名），第一期已实现。
> 基础：现有内部 Catálogo（`wholesale_views.py`，购物车、下单、订单状态、选款都已完成），以及 2026-11-05 的门户架构文档（不在仓库里）。本设计只写和那份文档不同、或需要落到这个代码库的部分。

## 1. 第一期做什么

让批发客户用自己的账号打开同一套 Catálogo：看自己的价格、加购物车、下单、查看和修改订单。内部的 Catálogo 预览（Ver como）保留给店里用。

不做：在线付款、邮件、一个客户多个采购员（数据结构留着以后加）、客户自助注册。

## 2. 店主已定（2026-11-07）

| 问题 | 决定 | 和架构文档的差别 |
|---|---|---|
| 登录 | 手机号 + 密码 | 文档用邮箱 |
| 邀请 | 系统生成链接，店主用 WhatsApp 发 | 文档用验证邮件 |
| 谁能被邀请 | 任何 Revenda 客户 | 文档要求先有一笔真实成交 |
| 客户价格 | 和 Pedido 相同：手动折扣与上次成交差额取较新的 | 文档只用手动折扣 |

## 3. 身份

新增 `CustomerAccount`：

| 字段 | 说明 |
|---|---|
| `user` | OneToOne 到 Django User；用户名由系统生成（`c-<id>`），不对外显示 |
| `customer` | ForeignKey 到 Customer，PROTECT，必须是 Revenda |
| `phone` | 规范化后的手机号（去掉空格和符号，补 `351`），唯一，用来登录 |
| `status` | `invited` / `active` / `suspended` |
| `invited_by`、`invited_at`、`activated_at`、`suspended_at` | 留痕 |

规则：

- 一个 User 不能同时是员工和客户：有 `CustomerAccount` 的 User 不能有 `is_staff`、`is_superuser` 或任何内部分组，反过来也一样。邀请和激活时都检查。
- 每个请求重新检查：账号 `active`、Customer 仍是 Revenda。停用后，已登录的会话下一次请求就进不去。
- 手机号相同的两个客户：不能同时开通，提示经理先处理。

## 4. 邀请和激活

1. 客户详情页（经理可见）新增 **Catalogue access** 区块：未开通时显示 **Create invite link**。
2. 系统生成一次性链接 `/b2b/invite/<token>/`，72 小时有效。数据库只存令牌的 SHA-256 摘要；再生成一次，旧链接立即失效。
3. 区块显示链接和 **Copy** 按钮，店主用 WhatsApp 发给客户。
4. 客户打开链接：显示店名和客户名称，填手机号（必须和档案里的一致）、设密码（输入两次，按 Django 密码规则校验）。
5. 提交后账号变 `active`，直接登录，进入目录。
6. 区块之后显示状态：Invited（可重新生成链接）、Active（可停用、可生成重设密码链接）、Suspended（可恢复）。

忘记密码：客户联系店里，店主在同一区块生成重设链接，流程和邀请相同。

## 5. 登录

- 地址：`/b2b/login/`，只有手机号和密码两个字段，葡萄牙语。
- 登录失败的提示统一为“手机号或密码不正确”，不透露手机号是否存在。
- 限流：同一手机号或同一 IP 15 分钟内失败 5 次，暂停 15 分钟。记录写入现有的登录失败日志（Audit → Errors）。
- 会话：14 天；退出按钮在页头。

## 6. 封闭内部入口

现在很多内部页面只要求登录。新增中间件做默认拒绝：

- 客户账号只能访问 `stock/middleware.py` 里 `CUSTOMER_PAGES` 列出的页面、静态文件和产品图片；其他页面的 GET 转回目录，其他请求返回 403。
- 未登录的人打开目录页面，转到客户登录页 `/b2b/login/`；员工照常用 `/login/`。
- 中间件只看“是不是客户账号”，不依赖每个视图自己写对权限，以后新增的内部页面也自动受保护。

## 7. 客户看到的页面

和内部 Catálogo 共用模板与服务，区别只在页头和身份来源：

| 页面 | 地址 | 说明 |
|---|---|---|
| 目录 | `/catalog/`（`/b2b/` 也转到这里） | 与 Catálogo 相同：类型、品牌、搜索、在路上、选款 |
| 购物车 | `/catalog/cart/` | 收货资料默认用客户档案 |
| 我的订单 | `/catalog/orders/` | 这个客户的申请和过去的销售 |
| 订单详情 | `/catalog/orders/<id>/` | 状态、修改、取消，规则与现在相同 |

实现时客户和员工共用 `/catalog/` 这些地址，同一个视图按登录身份决定客户是谁、用哪个页面框架；中间件按页面名称（不是地址前缀）放行，所以 `settings/catalog/` 之类的内部页面不会被误放行。

- 客户来自登录的账号，不读 session 里的 Ver como；客户不能通过改地址看到别的客户的数据。
- 页头：店铺 logo 或名称、客户名称、退出。没有内部侧边栏和底部导航。
- `OrderRequest.submitted_by` 是客户的 User，`customer` 来自账号。Order requests 和 Pedido 的处理流程不变。
- 价格、库存状态、选款和下单规则全部沿用 Settings → Rules 和现有服务。

## 8. 测试账号

`test_account create` 增加 `--customer <id>`：建一个绑定这个客户的客户账号（手机号用命令参数），用来从客户角度测试；`remove` 照常连同记录删除。

## 9. 上线前检查

- 客户账号打开任何内部地址都是 403（逐个检查菜单里的页面和 API）。
- 停用后下一次请求被拒。
- 邀请链接过期、重复使用、重新生成后旧链接都无效。
- 两个客户之间看不到对方的订单和价格。
- 手机和桌面截图检查登录、激活、目录、购物车、订单页。

## 10. 需要店主确认

- 第 4 节：邀请链接 72 小时有效是否合适。
- 第 5 节：会话 14 天是否合适（越长越方便，手机丢了风险越大）。
- 第 7 节：页头显示店名（不用 logo），取 Shop settings 里处理网上订单的那家店。
